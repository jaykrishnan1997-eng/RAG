## 1. The project in short

- The vLLM 0.10.1 repository (`data/raw/vllm-0.10.1/`) is only **data**. You read its files, chunk them, and index them. You never install, import or run vLLM.
- You build: `index`, `search`, `search_dataset`, `answer`, `answer_dataset`, `evaluate`, all via `uv run python -m src <command>` with Python Fire.
- Retrieval returns sources: `(file_path, first_character_index, last_character_index)`, each at most 2000 characters.
- Answers are generated by **Qwen/Qwen3-0.6B** (default, mandatory), from the retrieved chunks, running on CPU.
- Score: recall@5 on private datasets, at least **80% docs** and **50% code**. Indexing at most **5 minutes**. 200 questions retrieved in at most **90 seconds**.
- The evaluation is automated plus a live defense (14 pass/fail checks; the bonus is only graded if all pass).
- Time limit: 180 hours.

## 2. Terms that cause confusion

### 2.1 Characters vs tokens
| | Characters | LLM tokens | Search tokens |
|---|---|---|---|
| What | Every letter, digit, space, newline, symbol | Pieces made by a model's tokenizer | Words your own tokenizer produces for BM25 |
| Used for | **Chunk size limit (2000)** and **offsets** | Prompt budget for Qwen3-0.6B | The index |
| Counted by | `len(text)` on the raw slice | The model's tokenizer | Your tokenizer |

Blogs say "300 to 500 tokens". Translate that into character experiments (try 1000, 1500, 2000) and measure recall@5. Rough rule for English: one LLM token is about 4 characters; code has more tokens per character.

### 2.2 Chunking vs indexing (separate steps, run one after the other by `index`)
- **Chunking:** files in, chunk records out. A record holds file path, start and end character positions, the exact text slice, and optionally the heading path. It knows nothing about words or scores.
- **Indexing:** chunk records in, search structure out. It builds the text to index (slice plus heading path and file name tokens), tokenizes it, builds the BM25 data (term to chunks with frequency, chunk lengths, average length, document frequencies) and saves it to `data/processed/`.
- The link between them is the list of chunk records: each keeps its path and positions so search can report them.
- At search time neither step runs again: load the index, tokenize the query the same way, score, return the top k.

### 2.3 Reading a file vs cutting it
A 10,000-character file is read **once** into one string and cut into pieces. A structure-aware chunker usually yields more than 5 chunks (boundaries fall at functions or sections). Positions are just offsets into the same string.

## 3. Pipeline overview and what you store

```
data/raw  ->  [select files]  ->  [chunk: python | markdown/text]  ->  chunk records
          ->  [tokenize + build BM25 index]  ->  data/processed/
query     ->  [tokenize query]  ->  [score chunks]  ->  top-k sources  (search)
top-k     ->  [build prompt within token budget]  ->  Qwen3-0.6B  ->  answer  (answer)
results   ->  [moulinette / your evaluate]  ->  recall@k
```

Per chunk, store:
- `file_path` exactly as in the corpus (verbatim comparison by the grader)
- `first_character_index`, `last_character_index` in the original file
- the exact slice, or enough to re-read it later (see section 9)
- optionally: heading path, scope names (class, function), for the indexed text only

Decision to make and defend: store chunk text in the index (bigger index, faster answering) or re-read from `data/raw/` using offsets (smaller index, must read with the same newline and encoding settings).

## 4. Chunking: shared rules (both strategies)

1. **At most 2000 raw characters per chunk** (configurable by `--max_chunk_size`, default 2000, never above). One over-long source invalidates the whole output file.
2. **Exact offsets.** The reported range must be a real slice of the original file. Read files with `newline=""` so line endings are not translated. Use `encoding="utf-8"` and decide what to do with decode errors. A UTF-8 BOM counts as a character.
3. **Tile the file.** Chunks should be contiguous and cover the whole file, with no gaps, so nothing falls between chunks.
4. **Never strip, trim, normalise or rejoin text before computing offsets.** Many blog chunkers do (split lines, strip, rejoin with blank lines). That breaks offsets.
5. **Indexed text is separate from the reported range.** You may add file path, heading path and scope names to the text you tokenize. The reported positions and the 2000 limit apply only to the original slice.
6. **Hard-split fallback.** If a unit (code block, table, long line, single statement) is still over the limit, split by lines, then by characters. Do not emit oversized chunks.
7. **Never crash.** An unparsable or undecodable file falls back to the plain text splitter, or is skipped with a message.
8. **The two strategies must be genuinely different** (syntax-driven for Python, structure-driven for Markdown/text). They can share helpers (offset table, size cap, fallback).

Automated checks to run over the whole corpus (write these early):
- no chunk over 2000 characters
- chunks are contiguous and cover the file
- slicing the file at a chunk's offsets returns exactly its text
- no crash on any file
- chunking time fits in the 5-minute total budget

Chunk size and IoU: scoring counts a hit when the same file overlaps the ground-truth range with IoU of at least 0.05. Larger chunks inflate the union and lower IoU, so smaller chunks often score better. Example: ground truth [1000, 1500], chunk [1400, 3400]: intersection 100, union 2400, IoU about 0.042 (miss). Chunk [1300, 3300]: intersection 200, union 2000, IoU 0.1 (hit).

## 5. Chunking: Python files (AST-based recursive split-then-merge)

Idea: the same recursion as for text, but the boundaries come from the syntax tree.

**Algorithm (concept)**
1. Parse with the `ast` module. Top-level units: module docstring, imports, functions, async functions, classes, assignments, the `if __name__` block.
2. Merge neighbouring small units into one chunk up to the limit.
3. If a unit is over the limit, recurse into its children (class into methods, function into body statements, `if/for/try` into blocks).
4. If a leaf is still too big, split by lines, then by characters.
5. If parsing fails (`SyntaxError`, odd encoding, empty file), fall back to the text splitter for that file.

**Details that decide recall**
- A decorated function: `lineno` points at the `def` line, not the decorators. Take the earliest decorator line as the start.
- Comments and blank lines between nodes are not in the tree. Attach each gap to a neighbour (usually the following node) so the chunks tile the file.
- `lineno` is 1-based and `end_lineno` is inclusive. `col_offset` is in **UTF-8 bytes**, not characters. The safest approach is to cut only at line boundaries and use a table of line start offsets.
- Size is always the raw character length of the span (the moulinette checks raw characters).
- Merging unrelated functions dilutes BM25 scores. Test merging only siblings within the same parent, or only small units.
- For the indexed text, add file path tokens and scope names (for example `LLMEngine add_request`) so identifier queries match. These stay out of the offsets.

**Edge cases to test:** very long single lines, generated files, non-ASCII text, nested functions, `match` statements, files with only comments, huge string or data literals.

## 6. Chunking: Markdown and text files (structure-aware)

You said you use recursive chunking for text and Markdown. A structure-aware version uses headings as the highest-priority separator within the same recursive idea. One chunker can handle both file types, choosing behaviour by extension.

**Know what a Markdown file contains** (open 2 or 3 real files in `data/raw/vllm-0.10.1/docs/`)
- headings: lines starting with `#`, `##`, `###`
- paragraphs separated by blank lines
- fenced code blocks: a line with three backticks (or `~~~`), code, then a closing fence. A `#` line inside a fence is code, not a heading
- tables: consecutive lines starting with `|`, no blank lines
- lists: lines starting with `-`, `*` or `1.`
- maybe a settings block between `---` lines at the top of the file

**Algorithm (concept)**
1. Walk the file line by line, tracking the character position and whether you are inside a fence.
2. Cut at headings first (at the levels you choose). Keep the heading with its body.
3. If a section is over the limit, fall back through paragraphs, then lines, then sentences, then a hard character split.
4. Keep code fences, tables and list blocks whole when they fit. If one alone exceeds the limit, split inside it by blank lines or lines.
5. Merge tiny sections into a neighbour while the result fits (test whether this helps).
6. Overlap is optional and can crowd your top 5 with near-duplicates. Test it on and off. If used, extend the range backwards in the original text instead of copying text.

**Text files (`.txt`):** no heading logic (a `#` in a text file is usually a comment). Use paragraphs, then lines, then sentences.

**Indexed text extras:** the file name and path tokens (split on `/`, `_`, `-`, `.`), and the heading breadcrumb (for example `Features > LoRA > Serving`). Keep CLI flags such as `--max-num-seqs` as tokens and also split them on hyphens.

**What a record looks like (the shape you described, plus positions)**
- file path, start, end, exact slice, heading path (like `Header 1`, `Header 2`), indexed text.
- LangChain's `MarkdownHeaderTextSplitter` output is the model for the heading metadata, but its text is rebuilt and its docs state that the default strips whitespace and newlines, so it has no usable positions. Copy the idea of metadata, not the text handling.

**Checks to grep the corpus for, then handle by frequency**
- setext headings (`===` or `---` under a line)
- front matter at the top of files
- `~~~` fences, longer fences, unclosed fences, indented code blocks
- raw HTML blocks, comments, MkDocs-style syntax (`!!!` admonitions, tabs, snippet includes)
- very long lines (generated tables, badges, base64)
- empty files, BOM, CRLF line endings, tabs

## 7. Indexing and tokenization

**Tokenization (the vocabulary gap)** Questions may quote an identifier verbatim (`max_num_seqs`, `AsyncLLMEngine`) or paraphrase it ("maximum number of sequences"). So index both:
- the whole identifier, and
- its parts (split snake_case and CamelCase; lowercase).

Other choices to test one at a time: stop words, very short tokens, stemming (can hurt code identifiers, test docs and code separately), numbers and flags. Documents and queries must use the **same** tokenizer.

**Inverted index** A map from term to the chunks containing it (with term frequency). Also store each chunk's length, the average length, the total number of chunks and document frequencies. Retrieval only touches the lists of the query's terms, which is why it is fast.

**Persistence** Save everything under `data/processed/`. Loading must be fast and happen **once per dataset run**, not once per question (the 90-second limit includes it). Be ready to explain your format choice.

**BM25** score(D, Q) = sum over query terms t of IDF(t) * f(t,D)*(k1+1) / ( f(t,D) + k1*(1 - b + b*|D|/avgdl) )
- f(t,D): occurrences of t in chunk D; |D|: chunk length; avgdl: average chunk length.
- k1 (about 1.2 to 2.0): term-frequency saturation. b (about 0.5 to 0.9): length normalisation.
- IDF commonly log((N - n_t + 0.5)/(n_t + 0.5) + 1).
- Versus TF-IDF: BM25 saturates term frequency and normalises length properly.

## 8. Retrieval mechanisms, from baseline to bonus

1. **Baseline: BM25** with good tokenization. Tune `k1`, `b` per dataset type (docs vs code may differ).
2. **Cheap lexical improvements (first):** identifier splitting plus whole identifier; field boosts (file path, heading breadcrumb, class and function names; the idea behind BM25F); query cleaning (drop question words, keep identifiers, flags, numbers); verbatim-identifier boost; bigram or phrase bonus; light stemming (test).
3. **Ranking-level improvements (high value for this scoring rule):** file-level aggregation (best chunk plus a small bonus for other matching chunks in the file); two-stage retrieval (candidate files, then best chunks inside); cap chunks per file in the top 5 and test it; merge adjacent high-scoring chunks into one range (still under 2000).
4. **Query expansion (medium):** pseudo-relevance feedback (add distinctive terms from the top results and search again; costs a second pass against the 90-second budget); a small hand-made synonym list for vLLM vocabulary (can overfit the public questions).
5. **Bonus route (only after all mandatory checks pass):** dense embeddings with a small CPU model such as `all-MiniLM-L6-v2` (bonus 1); hybrid via Reciprocal Rank Fusion (bonus 2). Cross-encoder reranking is probably too slow on CPU. Semantic **chunking** (splitting by embedding similarity) is not worth it for the mandatory part: it needs embeddings at index time, risks the 5-minute limit, and docs already have heading boundaries.

**Suggested order:** BM25 plus tokenization and path/heading boost, then `k1`/`b`/chunk size, then file-level aggregation and per-file caps, then identifier boost and phrase bonus, then pseudo-relevance feedback if needed, then embeddings plus RRF as bonuses.

**Diagnose each miss by hand:** is the right file absent from the candidates (vocabulary problem), present but ranked low (ranking problem), or hit without overlap (chunk-boundary problem)?

## 9. Answer generation

- Load Qwen/Qwen3-0.6B (Hugging Face `transformers` plus `torch`, CPU). Load the model **once** per run.
- Qwen3 has a thinking mode; turn it off or strip it so reasoning text never ends up in `answer` (see the model card).
- Prompt design is graded: tell the model to answer only from the context and to say it does not know if the context lacks the answer; label each chunk with its file name; keep answers short; place the question clearly.
- Token budget: count in the model's tokens. Do not paste `k=10` chunks of 2000 characters blindly (the evaluator's demo uses `--k 10`). Decide how many chunks go into the prompt and how you truncate.
- The JSON output is produced by your code with the pydantic models; the model only writes the answer text.
- Read 20 or more answers by hand: look for leaked thinking text, repetition, empty or truncated answers, unrelated answers.

## 10. Evaluation: how you are really graded

**Recall@k:** for each question, the share of its correct sources found in your top k. A source counts as found when one of your results is in the **same file** (exact string) and overlaps its range with IoU at least 0.05. Averaged over questions. Multi-source questions need several hits.

**The 14 mandatory checks (all pass/fail; all must pass before the bonus)**
1. Setup: repo contains only requested files; Python 3.10+; uv; `pyproject.toml` and `uv.lock`; `src/`; Makefile; README; `uv sync` works from a fresh clone.
2. Launch pipeline: `exam_retrieval.sh` runs (index, search over private datasets, moulinette), about 8 minutes.
3. Code quality and pydantic: all 8 models; flake8 and mypy through `make lint`; Makefile rules (install, run, debug, clean, lint); try/except; context managers; tqdm; valid JSON output. **No import of the moulinette**: the evaluator greps for lines starting with `import moulinette` or `from moulinette` in `.py` files.
4. Chunking: at least 2 strategies; default 2000 and `--max_chunk_size`; explain chunk size impact; show both strategies' code.
5. Retrieval: BM25 or TF-IDF; explain it; live demo `search "How to configure OpenAI server?" --k 10`.
6. Answer generation: Qwen3-0.6B default; live demo `answer "How to configure OpenAI server?" --k 10`; within token limits.
7. Docs recall@5 at least 80% (private dataset).
8. Code recall@5 at least 50% (private dataset).
9. Indexing at most 300 seconds.
10. 200 questions retrieved in at most 90 seconds ("warm" throughput).
11. Answer quality: evaluator picks 3 answers, 2 must be satisfactory (coherent, mostly grounded, on point).
12. Understanding: 5 questions, 4 must be satisfactory.
13. README: 5 of 6 items (architecture, chunking, retrieval, performance, design decisions, example usage).
14. Edge cases: no traceback for `search ""`, `search "asdfghjkl"`, `answer "What is vLLM?" --k 0`, and `search_dataset --dataset_path /nonexistent.json` (with **only** the path, no `--k` or `--save_directory`).

**Public vs private data:** you only have the public datasets; grading uses private ones. Keep a held-out slice of the public questions while tuning.

## 14. Defense preparation

**The five questions (4 of 5 needed): points to cover in your own words**
1. *What is RAG and why useful?* Models are frozen in time and lack private data; retraining is costly; RAG fetches relevant text at question time, enabling fresh or private data, traceable sources, fewer hallucinations. Limits: bad retrieval means bad answers.
2. *Walk through the pipeline.* Corpus, file selection, two chunkers with offsets, tokenization, inverted index, persistence; at query time: tokenize, score, top-k, prompt, Qwen3-0.6B, pydantic-validated JSON; evaluation with recall@k and IoU.
3. *TF-IDF vs BM25.* Both lexical. TF-IDF: term frequency times IDF, grows without limit, weak length handling. BM25: saturation (`k1`) and length normalisation (`b`), probabilistic IDF.
4. *Implementation choices and trade-offs.* Which files indexed, chunk boundaries and size, identifier splitting, stop words, BM25 parameters, how many chunks go to the prompt, prompt wording, index format, speed vs recall. For each: what you tried, measured effect, what you gave up.
5. *What to improve with more time.* Embeddings plus hybrid, reranker, query expansion, better chunk context headers, overlap, caching, incremental indexing. Tie each to a failure you saw.

**Chunk size question:** too small loses context, adds noise and many chunks, and splits multi-part answers across competing results; too large dilutes scores, hurts IoU, hits the 2000 cap and fills the prompt with noise. Quote your own recall numbers.

**Recode step:** expect a small live change (BM25 parameter, a tokenizer rule, an output field, a chunk rule). Writing everything yourself is the best preparation.

## 15. Pitfalls

1. Wrong offsets after normalising text (silent recall killer).
2. Chunks over 2000 characters (invalidates the whole file).
3. `file_path` prefix mismatch (must equal the corpus path exactly).
4. Index only in memory, so `search` has nothing to load.
5. Reloading the index or the model for each question.
6. Different tokenization for documents and queries.
7. Ignoring identifiers.
8. Indexing everything (binary-like or huge generated files) and blowing the 5 minutes.
9. Tuning on one dataset only (docs and code behave differently); no hold-out.
10. Dropping "duplicate" chunks (a ground-truth chunk may be removed).
11. Missing `uv.lock` or a stale lockfile; committing data or weights.
12. Thinking text leaking into answers.
13. Untested empty or garbage query paths; `search_dataset` with only a bad path.
14. Leaving chunker tuning to the last week.
15. Copying a blog or repo chunker you cannot explain.
